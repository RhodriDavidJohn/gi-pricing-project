# GI Pricing

Motor insurance pricing on the French MTPL data (freMTPL2): frequency-severity pure premium
models, a GLM against XGBoost comparison, model selection, final training for live use, and a
Streamlit app that shows the selection, compares the models and quotes customers.

- **GLM**: Poisson or negative binomial frequency × Gamma or log-normal severity, on grouped
  rating factors with interactions chosen by BIC.
- **XGBoost**: simple (Poisson with exposure offset) or hurdle frequency × Gamma severity, on
  raw and categorical factors with a monotone bonus-malus effect.
- Every quote from either model can be broken down by customer detail (exact Shapley values).

Prices are annual **pure premiums** (expected claims cost), rebased to the portfolio loss level,
with a minimum premium. They don't include expenses, commission or profit.

## Setup

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

The data is downloaded from OpenML ([freMTPL2freq](https://www.openml.org/d/41214),
[freMTPL2sev](https://www.openml.org/d/41215)) by the first pipeline step, or on its own with
`python scripts/download_data.py` (`--force` to download again).

## Running

From the project folder:

```bash
python scripts/run_pipeline.py                                  # all steps
python scripts/run_pipeline.py --steps select_glm select_xgb     # some steps (always in pipeline order)

python scripts/download_data.py                                 # or one step at a time
python scripts/prepare_data.py
python scripts/select_glm.py
python scripts/select_xgb.py
python scripts/train_final.py
python scripts/report.py
```

The download step is skipped when the raw files already exist.

Every script takes `--config path/to/config.yaml` (default: `config.yaml` in the project
folder) and works from any folder. Relative paths in a config are resolved from its folder.
On macOS/Linux the scripts can also be run directly, e.g. `./scripts/run_pipeline.py`.

## Rating factors

Pre-processing follows the GLM case study on this data by Noll, Salzmann & Wüthrich,
[Case Study: French Motor Third-Party Liability Claims](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=3164764)
(2018). All thresholds are in the `features` section of `config.yaml`.

| Factor | GLM | XGBoost | Why |
|---|---|---|---|
| Claim count, exposure | capped at 4 and 1 | same | larger values are treated as data errors |
| Very short policies | dropped below `features.min_exposure` (0.02 years) | same | one claim on a few days of cover is a claim rate in the hundreds |
| Driver age | groups 18-20, 21-25, 26-30, 31-40, 41-50, 51-70, 71+ | raw age | risk is high and changes fast for young drivers, flat in mid-life |
| Vehicle age | groups 0, 1-10, 11+ | raw age | new vehicles behave differently from the rest |
| Vehicle power | groups 4 to 8, 9+ | raw power | few vehicles above 9 |
| Bonus-malus | capped at 150 | capped at 150, **constrained to increase** frequency | a worse claims record should never lower the price |
| Density | log | log | density is heavily skewed |
| Area | ordered code 1-6 | same | Area follows density |
| Brand, fuel, region | categories | categories | no natural order |
| Claim amounts (severity) | capped at the 99.5th percentile | same | a few very large claims otherwise dominate the severity fit |

- **Base levels.** GLM categories use the level with the most exposure as the base, so
  relativities read as "compared with the most common group". The final GLM's relativities
  are saved to `models/glm_relativities.csv`.
- **Large claims.** The cost above the claim cap isn't lost: the rebase factor is set on
  uncapped claims, so it spreads that cost across all policies as a flat loading.
- **Interactions.** Candidates, each with an actuarial reason, are listed in
  `glm.interactions_to_test`: bonus-malus by driver age (new drivers start at 100), young
  drivers in powerful or new cars, bonus-malus by density, and vehicle age by brand.
  Forward selection keeps only those that improve BIC by at least `glm.min_improvement`.
  With ~400k training policies, AIC would keep almost every multi-level interaction.
- **Claim counts vs claim amounts.** The two raw files disagree for some policies (a claim with
  no amount, or an amount with no claim count). The cleaning step logs how many, since frequency
  is fitted to `ClaimNb` and severity to the claim amounts.
- **Encoding.** Category levels and the claim cap are saved with the processed data
  (`feature_info.json`) and with each final model, so a single quote is encoded exactly like
  the training data.
- **The notebook's original flags** (young driver, new vehicle, etc.) are still built and used
  in the interaction candidates.

## Model selection

`select_glm.py` and `select_xgb.py` use the same seeded 60/20/20 train/validation/test split,
stratified on whether a policy claimed.

| | GLM | XGBoost |
|---|---|---|
| Terms / settings | interactions by forward BIC (or AIC) on train | `xgb.param_grid`, early stopping on validation, lowest validation deviance (log loss for the hurdle classifier) |
| Frequency candidates | Poisson, negative binomial (alpha estimated) | simple, hurdle |
| Severity candidates | Gamma, log-normal | Gamma |
| Component comparison | validation deviance (reported) | validation deviance (reported) |
| Pair chosen by | validation pure premium Gini | validation pure premium Gini |
| Reported on test | loss ratios, Gini, deciles, tariff | same, plus hurdle calibration plot |

Ties in Gini (to 4 decimal places) go to the simpler model (Poisson, simple). The choice is
saved to `outputs/selection/<model>/selected.yaml`, which `train_final.py` reads. Deviance and
Gini can disagree: deviance measures how accurate the predictions are, Gini how well they rank
risks. If they point different ways, check `metrics.json` and `pair_comparison_val.csv`
before accepting the choice. To fix a choice by hand, edit `selected.yaml`.

With the default grid (2 × 2 settings, up to 1,000 trees) the XGBoost step fits 16 models.
Add values to `xgb.param_grid` to search more widely; the run time grows with each combination.

## Report

`report.py` compares the selected GLM and XGBoost models on the test set (the same policies for
both) and writes `reports/results.md`, `reports/figures/` and `reports/tables/`:

| Chart | What it shows |
|---|---|
| Lorenz curves | how well each model ranks risks (Gini) |
| Lift charts | actual vs predicted cost by band of predicted premium |
| Double lift | where the two models disagree, which one follows actual experience |
| Actual vs expected by factor | fit by driver age, vehicle age, bonus-malus, etc., with exposure underneath; also `Area` and `Region`, which the models don't use |
| Price changes | share of policies whose premium would move, and by how much, if XGBoost replaced the GLM |
| Price response curves | how each final model's premium changes with one detail at a time |
| GLM explanations | why an example customer pays what they pay |
| Claim sizes | the claim amount distribution and the share of cost from large claims |
| Hurdle calibration | predicted vs observed claim probability (when the hurdle model is chosen) |

Every number in `results.md` is calculated from the run. The **Discussion** section is left
for your own interpretation - fill it in after each full run. Bands, example customers and the
large claim percentile are set in the `report` section of `config.yaml`.

To publish the results, commit `reports/` after running the pipeline on the full data.

## Final training and live data

`train_final.py` reads the raw files in `paths.raw_dir`, fits the selected models on all the
data except a stratified holdout (`final.holdout_size`, default 10%), and uses the holdout for
XGBoost early stopping and calibration, the rebase factor and the minimum premium.

For live data, copy `config.yaml` (e.g. `live_config.yaml`), point `raw_dir` and `model_dir` at
the live locations, and run:

```bash
python scripts/train_final.py --config live_config.yaml
```

Each model is saved as `<model_dir>/<name>.joblib` with a `<name>_card.json` recording when and
on what it was trained, the selected specification, the rebase factor, the minimum premium,
the holdout results, the customer input ranges and an example quote. The GLM file holds only
coefficients, so it is a few KB.

## Quoting customers

`quote.py` previews what the app will do:

```bash
python scripts/quote.py --model glm --help                       # details and allowed ranges
python scripts/quote.py --model glm --DrivAge 22 --VehPower 9    # quote (other details default)
python scripts/quote.py --model glm --DrivAge 22 --change DrivAge=40 --change BonusMalus=50
python scripts/quote.py --model xgb --DrivAge 22 --explain       # effect of each detail
python scripts/quote.py --model xgb --DrivAge 22 --curve DrivAge # price across a detail's range
```

The customer details are `DrivAge`, `BonusMalus`, `VehAge`, `VehPower`, `VehBrand`, `VehGas`,
`Density`, `Area` and `Region`; the features are built from them in the same way as for training.

### The model object

Everything the app uses is on the model object (`scripts/lib/pricing_model.py`), loaded with
`load_pricing_model("models/glm.joblib")`:

- `input_fields`: each detail's type, min/max or options, and default.
- `quote(customers)`: a dict (one customer) or DataFrame (several). Returns annual frequency,
  average claim cost, pure premium, annual and monthly premium, and whether the minimum
  premium applied.
- `price_curve(customer, detail, values=None)`: quotes across a detail's range, with a
  log-spaced grid for details like Density. To show a price change, quote before and after
  (the app shows this against the typical customer).
- `explain(customer, reference=None)` (both models): each detail's effect on the premium
  compared with a reference customer (by default the typical customer: the median or most
  common value of each detail).
  - **How it works.** The model is quoted for every mix of the two customers' details, and each
    detail gets its exact Shapley value for log(premium): its average effect over all the mixes.
    With 9 details that is at most 512 quotes.
  - **Output.** `base_premium × product of Factor = pure_premium` exactly, and the effects are
    split into frequency and severity. `PremiumImpact` shares the difference out in currency,
    ready for a waterfall chart.
  - **Any model.** The method doesn't depend on the model, so it covers the hurdle model too
    (its TreeSHAP values wouldn't add up to the premium).
- `relativities()` (GLM): the multiplicative factor for every coefficient.
- `calculation(customer)` (GLM): the quote step by step - each term's value, coefficient and
  factor, then frequency × severity × smearing × rebase.

## Streamlit app

Run the pipeline first, then from the project folder:

```bash
streamlit run app/streamlit_app.py
```

| Page | What it shows |
|---|---|
| **Overview** | Test Gini and loss ratio for each model, the chosen models, links to the other pages |
| **Model selection** | GLM: candidate interactions and why, the forward selection steps, Poisson vs negative binomial, Gamma vs log-normal, the pair chosen by validation Gini. XGBoost: the grid search heatmaps, simple vs hurdle frequency, the pair chosen |
| **GLM vs XGBoost** | Performance on the test set (Lorenz, lift, double lift, actual vs expected by factor, price changes) and interpretability (GLM relativities, price response to each detail, the same customer explained by both models) |
| **Get a quote** | Enter the customer's details in the sidebar and the price updates straight away. The GLM is used by default, with a toggle for XGBoost. A waterfall shows how each detail moved the price from the typical customer; for the GLM the full calculation is shown too. A what-if chart shows the price across one detail's range |

The app only reads the files the pipeline writes (`models/`, `outputs/selection/`,
`reports/tables/`) and shows instructions if they are missing. To use another config, set
`GI_PRICING_CONFIG=path/to/config.yaml`.

### Deploying to Streamlit Community Cloud

1. Run the pipeline on the real data and commit `models/`, `outputs/selection/` and `reports/`.
   The large per-policy files (`test_predictions.csv`, `tariff_sheet.csv`) are in `.gitignore`;
   the raw and processed data are not committed.
2. Pin `requirements.txt` to the versions the models were trained with (`pip freeze`), since the
   models are pickled and may not load under other versions of xgboost or scikit-learn.
3. On [share.streamlit.io](https://share.streamlit.io), create an app from the repository with
   main file path `app/streamlit_app.py`, and choose the Python version you trained with.

## Tests

The tests use synthetic data with the freMTPL2 columns (and a stand-in for OpenML), so they
run without downloading anything:

```bash
pytest
```

`tests/test_app.py` runs the pipeline on synthetic data, then opens every app page headless
(Streamlit's `AppTest`) and checks that the quote changes when details or the model change.

## Still worth revisiting

- **Fix the chosen terms for production.** Selection runs each time `select_glm.py` runs.
  Review the chosen interactions and consider fixing them in `selected.yaml`.
- **Groups and caps** come from the case study. Check the one-way actual vs expected charts on
  the real data before changing them (e.g. merging thin groups).
- **Large claim loading.** The cost above the cap is spread as a flat loading. A separate
  large-claim model, or a loading that varies by risk, would be more refined. The cap percentile
  is taken from all claims before the split, a small leak into the test set.
- **Region** has ~20 levels in the real data. If some are thin, grouping them (or credibility
  weighting) would steady their relativities.
- **Hurdle calibration** is fitted and scored on the same validation data during selection,
  which slightly flatters the hurdle model's log loss.
- The `all_monthly` result assumes every policyholder pays monthly, while the 6% loading
  assumes half do.
- After the minimum premium is applied, other premiums aren't reduced to keep the portfolio
  total unchanged.
